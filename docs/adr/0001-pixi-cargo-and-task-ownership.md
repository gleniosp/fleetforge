# ADR 0001 — Pixi, Cargo, and task ownership

- **Date:** 2026-10-19

## Context

Contributors need consistent system/toolchain dependencies, Rust package builds,
and language checks. Robots need reproducible application runtimes without carrying
the contributor toolset. Multiple package managers must have clear ownership.

## Decision

Root `pixi.toml` is the canonical tooling/task entry point. Use composable features
for a shared Rust toolchain and contributor tools, with named `dev` and `build`
environments and explicit default-feature/task routing. Keep common package
versions aligned with an appropriate solve group. Build excludes dev-only tools.

Cargo owns Rust dependencies/builds/tests. Start with a virtual workspace and one
meaningful `fleetforge-agent` executable, Rust edition 2024 and explicit resolver 3.
Pin a compatible stable toolchain through Pixi after a clean-environment experiment;
do not introduce a competing rustup toolchain path. Share metadata/lints and inherit
them explicitly. Forbid unsafe code in the initial project packages; use rustfmt
and Clippy without blanket pedantic policies.

The dev environment includes prek and Commitizen. `prek.toml` owns project hooks;
pre-commit checks source/configuration, commit-msg validates Conventional Commits.
CI runs the same checks plus commit-range validation. Add Ruff lint/format and mypy
with Python code, and frontend tooling with SvelteKit. Put Python tool settings in
`pyproject.toml`. Minimal EditorConfig defaults help editors; language formatters
remain authoritative, and supported editor properties must agree with them.

Each workload release has a separate runtime workspace and lockfile. The root
workspace owns `pixi.lock`; Cargo owns `Cargo.lock`; the frontend will own its npm
lockfile. Commit relevant locks. Use locked Pixi/Cargo validation so checks reject
resolution drift rather than silently rewriting locks. Environments/caches/build
outputs may be generated by checks; tracked source and locks may not change.

Task families are `check`, `lint`, `format`, `format-check`, `fix`, `test`, `build`,
and safe `clean`, with component-prefixed tasks. Root tasks cover all implemented
components. Introduce `dev`, infrastructure, integration, and end-to-end tasks only
with real workflows/suites. Define each task's tool, scope, mutation, exit behavior,
and milestone when implemented. Ordinary clean/shutdown preserves operational
databases, releases, and caches; reset is distinct.

## Alternatives and consequences

A host-managed Rust/tool stack is familiar but leaves the clean setup dependent on
machine configuration. A single dev/runtime environment would leak contributor
dependencies into releases. Separate unrelated tool/CI commands would duplicate
policy. The chosen boundary adds Pixi resolution and routing to learn, but keeps
tooling, source builds, and deployment inputs reproducible and inspectable.

Exact tool versions, package availability, platform requirements, and hook behavior
must be tested before claiming support. Initially target Linux x86-64 only. Extract
additional crates/environments when actual dependency or component differences
justify them, rather than copying a prospective final directory tree.

## Evidence and revisit conditions

Consulted official [Pixi environment documentation](https://pixi.prefix.dev/latest/workspace/multi_environment/)
for feature/environment composition and
[Cargo workspace documentation](https://doc.rust-lang.org/cargo/reference/workspaces.html)
for explicit virtual-workspace resolver and inheritance behavior. These establish
available mechanisms, not that FleetForge configuration exists or passes checks.

Validate the complete toolset with host compiler shims unavailable, a fresh locked
install, and executable checks. Revisit package/version/routing decisions when that
experiment fails or an implemented component has materially different needs.
